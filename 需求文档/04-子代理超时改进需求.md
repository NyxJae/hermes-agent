## 一、需求概述

当前 Hermes Agent 的子代理（`delegate_task`）在超时后硬性中断，返回 `summary: null`，导致所有阶段性成果丢失。本需求要求改进超时机制：子代理超时后仍中断任务，但触发一条系统通知，让子代理立即总结阶段性成果、说明任务卡点并给出建议，然后返回给父代理。

**核心原则：**
- 超时仍要中断，防止无限运行
- 但中断前必须产出阶段性结果
- 返回结构保持不变，仅 `summary` 字段从 `null` 变为结构化内容

## 二、问题描述

### 2.1 当前行为

```json
{
  "task_index": 0,
  "status": "timeout",
  "summary": null,
  "error": "Subagent timed out after 600.0s with 10 API call(s) completed",
  "exit_reason": "timeout",
  "api_calls": 10,
  "duration_seconds": 600.07,
  "diagnostic_path": null
}
```

**问题：**
- `summary` 为 `null` — 阶段性成果全部丢失
- 父代理无法知道子代理卡在哪一步
- 无法给出下一步建议

### 2.2 期望行为

```json
{
  "task_index": 0,
  "status": "timeout",
  "summary": "## 阶段性成果\n已完成 GitHub API 搜索，找到 3 个相关 issue...\n\n## 任务卡点\n`browser_navigate` 访问 GitHub 页面时超时...\n\n## 建议\n建议将任务拆分为更小的子任务后再次分发",
  "error": "Subagent timed out after 600.0s with 10 API call(s) completed",
  "exit_reason": "timeout",
  "api_calls": 10,
  "duration_seconds": 600.07,
  "diagnostic_path": null
}
```

## 三、实现方案

### 3.1 实现方式

**必须在核心代码中实现**，不能仅靠插件。原因：

1. **时机精准控制**：需要在工具返回后、下一次 API 调用前插入消息，这个时机点在 `run_conversation` 的 while 循环内部
2. **状态访问**：需要访问子代理的内部状态（超时标志、剩余宽限时间）
3. **流程控制**：需要控制是否继续循环、是否强制中断

### 3.2 触发时机

```
while 循环内：
  1. 检查是否超时（600秒）
  2. 如果超时且未触发过通知：
     a. 设置 _timeout_notified = True
     b. 设置 _grace_until = now + 60秒
     c. 在下一次 API 调用前，通过 transform_messages 钩子插入超时通知
  3. 如果已通知且超过宽限时间（60秒）：
     a. 强制中断循环
     b. 返回已生成的 summary（如果有）或兜底文本
```

### 3.3 消息插入机制

利用 03-需求的 `transform_messages` 钩子插入超时通知：

```python
# 在 run_conversation 的 while 循环内，api_messages 构建后：

if getattr(self, '_timeout_notified', False) and not getattr(self, '_timeout_summary_generated', False):
    # 通过 transform_messages 钩子插入超时通知
    # 通知内容要求子代理生成阶段性总结
    pass
```

超时通知内容（作为 user 消息插入）：

```markdown
【系统通知】你的任务已超时（600秒），请不要再调用任何工具，直接按如下格式回复：

## 阶段性成果
[总结已完成的工作内容，尽可能详细]

## 任务卡点
[说明当前卡在哪一步，为什么卡住]

## 建议
[给主代理的简要建议，例如："建议将任务拆分为更小的子任务后再次分发"]
```

### 3.4 宽限机制

- 超时后给予 **60 秒宽限时间**
- 宽限期内子代理应生成总结回复（不调用工具）
- 60 秒后无论是否生成总结，强制中断
- 如果子代理在宽限期内仍调用工具，立即强制中断

### 3.5 子代理响应处理

子代理收到通知后：
1. 理解到已超时，停止工具调用
2. 生成结构化回复（阶段性成果 + 卡点 + 建议）
3. 作为 assistant 消息返回
4. 核心代码捕获该回复，提取为 `summary`

### 3.6 父代理接收

父代理收到的 `delegate_task` 返回：
- `status`: 仍为 `"timeout"`
- `summary`: 包含结构化内容（不再是 `null`）
- `error`: 保留超时错误信息
- 其他字段保持不变

## 四、边界情况

| 场景 | 预期行为 |
|------|----------|
| 子代理在 600 秒时正在执行工具 | 不强行打断，等待工具返回后，在下一次 API 调用前插入超时通知 |
| 子代理收到通知后仍调用工具 | 检测到工具调用意图时立即强制中断，返回 `"summary": "[强制中断，无法生成阶段性结果]"` |
| 子代理在 600 秒前已完成 | 正常返回，不会触发超时通知 |
| 子代理生成结果超过 60 秒宽限 | 强制中断，返回已生成的部分（如果有）或兜底文本 |
| 子代理在宽限期内正常生成总结 | 提取总结作为 `summary`，正常返回 |

## 六、超时机制详细设计

### 6.1 双层超时架构

| 层级 | 超时时间 | 作用 | 实现位置 |
|------|----------|------|----------|
| **内部超时** | `child_timeout_seconds`（默认 600s） | 子代理正常工作时间 | `AIAgent.run_conversation()` |
| **收尾宽限** | 固定 60s | 超时后生成总结的最长时间 | `AIAgent.run_conversation()` |
| **外部兜底** | `child_timeout_seconds × 2`（默认 1200s） | 防止内部未成功停止 | `delegate_tool.py` |

### 6.2 内部超时流程

```
0 ─────600s─────► 触发超时提醒，进入收尾阶段
                  │
                  ▼
              收尾阶段（最多60s）
              - 等待当前工具/API返回（各自有独立超时）
              - 生成阶段性总结
              - 子agent若调用新工具，立即强制中断
                  │
                  ▼
600s+60s ──────► 内部强制停止
                  │
                  ▼
1200s ──────────► delegate_tool 兜底杀死（理论上不会走到）
```

### 6.3 超时触发条件

**触发时机：**
- 在 `run_conversation` 的 while 循环内，每次工具返回后检查
- 如果 `elapsed >= child_timeout_seconds` 且未触发过超时通知：
  1. 设置 `_timeout_triggered = True`
  2. 设置 `_grace_until = now + 60s`
  3. 通过 `transform_messages` 钩子插入超时通知（user 消息）

**收尾阶段规则：**
- 60s 宽限只给"生成总结"，不等待新工具调用
- 如果子agent在宽限期内调用工具，立即强制中断
- 如果子agent在宽限期内生成无工具调用的回复，视为正常结束

### 6.4 超时通知文案

代码中写死，通过 `transform_messages` 钩子插入为 user 消息：

```markdown
【系统通知】你的任务已超时，请立即停止当前工作不要再调用任何工具了。

请按以下格式回复：

## 阶段性成果
[总结已完成的工作内容，尽可能详细]

## 任务卡点
[说明当前卡在哪一步，为什么卡住]

## 建议
[给主代理的简要建议，例如："建议将任务拆分为更小的子任务后再次分发"]

## 其他
[根据实际情况可酌情添加其他需要汇报的内容]
```

### 6.5 返回状态规则

子agent因超时而停止工作并生成阶段性总结后：
- `status`: 仍为 `"timeout"`（不是 `"completed"`，表示任务未完成）
- `summary`: 包含结构化总结内容（不再是 `null`）
- `error`: 保留超时错误信息
- 其他字段保持不变

### 6.6 外部兜底超时

`delegate_tool.py` 中的超时改为动态计算：

```python
# 原：
timeout = config.child_timeout_seconds or DEFAULT_CHILD_TIMEOUT

# 改为：
internal_timeout = config.child_timeout_seconds or DEFAULT_CHILD_TIMEOUT  # 600s
hard_timeout = internal_timeout * 2  # 1200s，兜底用
```
